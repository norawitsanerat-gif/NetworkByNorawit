TRANSPORT LAYER · FUNCTIONS

หน้าที่ของ Transport Layer

ชั้นที่ทำให้ "โปรแกรม (Process)" บนเครื่องต่าง ๆ คุยกันได้ — ทำงานใน Host ไม่ใช่ Router

1. เชื่อม Process ต่อ Process

การสื่อสารจริง ๆ คือระหว่าง Process กับ Process — Transport ใช้หมายเลขพอร์ตระบุว่าแอปไหนต้องรับ

2. Multiplexing / Demultiplexing

รวมข้อมูลจากหลายแอปส่งลงเครือข่ายเดียว (Mux) และแยกไปยังแอปปลายทางที่ถูกต้อง (Demux)

3. Reliability (เฉพาะ TCP)

ตรวจข้อผิดพลาด ส่งซ้ำเมื่อหาย และจัดลำดับข้อมูลให้ถูกต้อง — UDP ไม่มี

4. Flow & Congestion Control (TCP)

ไม่ส่งเกิน buffer ฝั่งรับ (Flow) และไม่ทำให้เครือข่ายแน่นเกินไป (Congestion)

จำง่ายTransport = "ชั้นที่ทำงานในเครื่องปลายทาง" — Router สนใจแค่ Network Layer (IP) ไม่เปิดดู Segment ข้างใน
Exam TipPDU ของ Transport Layer เรียกว่า Segment — ข้อสอบชอบถามชื่อ PDU ของแต่ละชั้น

MULTIPLEXING / DEMULTIPLEXING

Multiplexing / Demultiplexing (Mux / Demux)

หลายแอปใช้เครือข่ายเดียวกันได้ยังไง — รวมฝั่งส่ง แยกฝั่งรับ

MULTIPLEXING (ฝั่งส่ง) · DEMULTIPLEXING (ฝั่งรับ)

Multiplexing

ฝั่งส่งรวมข้อมูลจากหลาย Socket/Process ลงสู่ ช่องทางเดียว (หนึ่งเครือข่าย) — ประหยัดทรัพยากร เพราะไม่ต้องมีสาย/ช่องทางแยกต่อแอป

Demultiplexing

ฝั่งรับใช้ข้อมูลใน Header (Source/Destination Port) เพื่อแยกข้อมูลไปยัง Socket/Process ที่ถูกต้อง

จำMux = "รวมหลาย ๆ อย่างเป็นหนึ่ง" · Demux = "แยกหนึ่งเป็นหลาย ๆ" — ฝั่งส่ง Mux, ฝั่งรับ Demux

PORTS

Source Port / Destination Port

สองช่องแรกใน TCP/UDP Header — ระบุว่า "แอปไหนส่ง" และ "แอปไหนรับ"

Source Port

หมายเลขพอร์ตของ Process ต้นทาง — ฝั่งรับใช้ค่านี้เพื่อตอบกลับ (กลายเป็น Destination Port ของฝั่งตรงข้าม)

💡 มักเป็น Ephemeral Port (เลขสูง, ชั่วคราว) ที่ OS สุ่มให้ เช่น 54321

Destination Port

หมายเลขพอร์ตของ Process ปลายทาง — มักเป็น Well-Known Port (เลขต่ำ, มาตรฐาน) เช่น 80 = HTTP, 443 = HTTPS, 53 = DNS

SEGMENT · ใน TCP/UDP Header
Source Portเช่น 54321 (ของแอปเรา)
Destination Portเช่น 80 (HTTP)
... Payload (ข้อมูล)เนื้อหาของแอป
อุปมาเหมือนซองจดหมาย: From (Source) + To (Destination) — ไปรษณีย์ (Demux) อ่านที่อยู่แล้วส่งให้ห้องที่ถูกต้อง

TCP DEMULTIPLEXING

TCP Demultiplexing และ 4-tuple

TCP มีหลาย connection พร้อมกัน — ต้องใช้ 4 ค่าเพื่อระบุให้ไม่ซ้ำกัน

4-tuple ที่ใช้ระบุ TCP Connection

Source IP + Source Port + Dest IP + Dest Port

TCP Demultiplexing ใช้ครบทั้ง 4 ค่า เพราะฝั่งรับอาจมีหลาย connection ที่ใช้ Destination Port เดียวกัน (เช่น มี 100 การเชื่อมต่อมาที่ Port 80) — ต้องแยกด้วย Source IP/Port ด้วย

ตัวอย่าง 2 Connection ที่ Port เดียวกัน

Conn 1: (10.0.0.5 : 51000 → 1.2.3.4 : 80)
Conn 2: (10.0.0.5 : 51001 → 1.2.3.4 : 80)

ปลายทางเหมือนกัน (1.2.3.4:80) แต่ Source Port ต่างกัน → เป็นคนละ Connection

UDP ใช้แค่ 2 ค่า

UDP Demultiplexing ใช้แค่ (Dest IP, Dest Port) — เพราะ UDP ไม่มี "Connection" ที่ต้องแยก จึงง่ายและเบากว่า TCP

จำTCP = 4-tuple · UDP = 2-tuple — เพราะ TCP ต้องรู้จักแต่ละ Connection

TCP vs UDP

TCP vs UDP — เลือกใช้ตามแอป

สองโปรโตคอลหลักของ Transport — ดูความต่างเพื่อเลือกให้ถูกกับงาน

TCP — เชื่อถือได้

Connection-orientedต้อง Three-Way Handshake ก่อนส่ง
Reliableส่งซ้ำเมื่อหาย, จัดลำดับให้ถูกต้อง
Flow & Congestion Controlไม่ล้น buffer ฝั่งรับ / ไม่ทำให้เครือข่ายแน่น
Header ใหญ่20–60 ไบต์

UDP — เร็ว / เบา

Connectionlessไม่ต้องเปิดการเชื่อมต่อ ส่งได้ทันที
ไม่รับประกันอาจหาย/ไม่เรียงลำดับ (มีแค่ Checksum)
ไม่มี Flow/Congestionส่งตามอัตราที่แอปต้องการ
Header เล็กแค่ 8 ไบต์
ใช้ TCP เมื่อโอนไฟล์, เว็บ, อีเมล (ทน loss ไม่ได้) · ใช้ UDP เมื่อเกม, วิดีโอคอล, สตรีมสด, DNS (ต้องการความเร็ว/Delay ต่ำ)

UDP HEADER

UDP Header (8 ไบต์)

เรียบง่ายที่สุด — แค่ 4 ช่อง ๆ ละ 2 ไบต์ — กดแต่ละช่องเพื่อดูรายละเอียด

UDP SEGMENT · คลิกช่องเพื่อดูรายละเอียด
Source Port16 bits
Dest Port16 bits
Length16 bits
Checksum16 bits
Payload (ข้อมูล)ขนาดตามแอป

— กดที่ช่อง Header เพื่อดูรายละเอียด —

จำUDP Header = 8 ไบต์ (4 × 2 ไบต์) — เทียบกับ TCP ที่ 20+ ไบต์ จึงเบาและเร็ว เหมาะกับงานที่ต้องการความเร็ว

UDP CHECKSUM

UDP Checksum — ตรวจจับความผิดพลาด

วิธีง่าย ๆ ตรวจว่าข้อมูลเปลี่ยนไประหว่างทางหรือไม่ (detect เท่านั้น ไม่แก้ไข)

ตรงกัน = น่าจะถูก · ไม่ตรง = ข้อมูลเสีย → UDP แค่ทิ้ง (ไม่ส่งซ้ำให้ ต่างจาก TCP)

หลักการคร่าว ๆ

รวมข้อมูลเป็น ชุด 16 บิต แล้วใช้ 1's complement — หักล้างเลขไป-มา จนได้ค่าเดียว ถ้าข้อมูลถูกแก้แม้ 1 บิต ค่าที่คำนวณใหม่จะไม่ตรง

Exam TipChecksum ตรวจจับ Bit Error ได้ แต่ไม่สามารถแก้ไขหรือส่งซ้ำได้ — การส่งซ้ำเป็นหน้าที่ของ TCP
จำUDP = "ตรวจได้ แต่ไม่แก้งาน" · TCP = "ตรวจได้ แล้วยังส่งซ้ำให้จนกว่าจะถูก"

RELIABLE DATA TRANSFER

TCP Reliability + rdt (Reliable Data Transfer)

TCP ทำยังไงให้ข้อมูลถึงครบและถูกต้อง — ใช้กลไกหลายอย่างร่วมกัน

Checksum

ตรวจว่าข้อมูลเสียไหม

Seq #

เรียงลำดับข้อมูลถูกต้อง

ACK

ยืนยันว่าได้รับแล้ว

Timer + ส่งซ้ำ

หมดเวลา/หาย → ส่งใหม่

rdt1.0 — ส่งอย่างเดียว

สมมติว่าช่องทาง สมบูรณ์แบบ: ไม่หาย ไม่เสีย ไม่ผิดลำดับ → ผู้ส่งแค่ส่งไป ผู้รับแค่รับ ไม่ต้องมีอะไรตรวจสอบ

rdt2.0 — ตรวจ + ตอบกลับ

ช่องทางอาจมี Bit Error → เพิ่ม Error Detection (Checksum) และ ACK/NAK: รับถูก → ACK, รับเสีย → NAK แล้วผู้ส่งส่งใหม่

จำrdt2.0 มีปัญหา "ACK/NAK เสียหาย" → แก้ด้วยการเพิ่มหมายเลขใน packet (rdt2.1/2.2) แล้วพัฒนาเป็น rdt3.0 (มี Timer)
Exam Tipลำดับวิวัฒนาการ: rdt1.0 (ไม่ตรวจ) → rdt2.0 (ACK/NAK) → rdt3.0 (+ Timer) — ข้อสอบชอบถามว่า "รุ่นไหนเพิ่มอะไร"

ACK / NAK

ACK / NAK — feedback จากผู้รับ

ผู้รับบอกผู้ส่งว่าข้อมูล "ถึงดี" หรือ "เสีย ขอใหม่" — หัวใจของความเชื่อถือได้

ACK — ยืนยันรับแล้ว

Acknowledgment — ผู้รับตอบว่า "ได้รับข้อมูลถูกต้องแล้ว" ผู้ส่งจึงส่งชุดถัดไปได้

ใน TCP ใช้ Cumulative ACK — ACK หนึ่งค่าบอกว่า "รับครบจนถึงไบต์นี้แล้ว"

NAK — ข้อมูลเสีย ขอใหม่

Negative Acknowledgment — ผู้รับตรวจ Checksum แล้วพบว่าข้อมูลเสีย → ขอให้ผู้ส่งส่งใหม่

rdt2.0 ใช้ทั้ง ACK และ NAK แต่ TCP ในความเป็นจริงใช้แค่ ACK + Timeout/Dup-ACK (ไม่มี NAK)

SEQ / ACK

Sequence Number / Acknowledgment Number

ตัวเลขสองช่องใน TCP Header ที่ทำให้ "เรียงลำดับได้" และ "รู้ว่าส่งถึงไหนแล้ว"

Sequence Number (Seq #)

เลขลำดับของ ไบต์แรก ของข้อมูลใน Segment นี้ — ผู้รับใช้จัดเรียงข้อมูลให้ถูกต้องตามเดิม

💡 ข้อมูลถูกนับเป็นไบต์: ถ้า Segment นี้เริ่มที่ไบต์ 0 มี 1000 ไบต์ → Segment ถัดไปเริ่มที่ Seq 1000

Acknowledgment Number (Ack #)

บอกว่า "พร้อมรับไบต์ถัดไป" = Seq# ที่ได้รับ + จำนวนไบต์ที่รับได้ (Cumulative)

💡 รับครบไบต์ 0–999 → Ack = 1000 (หมายถึงถัดไปขอไบต์ 1000)

ตัวอย่าง · Sender ส่ง 1000 ไบต์ (Seq = 0)

Exam TipSeq# บอก "เริ่มที่ไบต์ไหน" · Ack# บอก "จบถึงไหนแล้ว (cumulative)" — Ack# = Seq# + จำนวนไบต์ที่รับ

CUMULATIVE ACK · WORKED EXAMPLE

การคำนวณ ACK จากจำนวน Byte

ตัวอย่างการคิด ACK# แบบ Cumulative — ทำตามแล้วจะเข้าใจเอง

โจทย์

Sender ส่งข้อมูล 3 Segment ขนาด 1,000 ไบต์ ต่อชิ้น โดยเริ่ม Seq = 0

Segment 1Seq = 0 (ไบต์ 0–999)
Segment 2Seq = 1000 (ไบต์ 1000–1999)
Segment 3Seq = 2000 (ไบต์ 2000–2999)

วิธีคิด

Ack# = Seq# ของ Segment + จำนวนไบต์ที่รับใน Segment นั้น

รับ Segment 1Ack = 0 + 1000 = 1000
รับ Segment 2Ack = 1000 + 1000 = 2000
รับ Segment 3Ack = 2000 + 1000 = 3000

เทคนิคลัด

Cumulative ACK = "ไบต์ถัดไปที่ยังไม่ได้รับ" — รับครบจนถึงไบต์ 2999 → Ack = 3000

ถ้า ACK ย้อนกลับมาเป็นค่าต่ำ (เช่น 1000 ซ้ำ ๆ) แปลว่ายังมี Segment ที่ยังมาไม่ถึง — นั่นคือจุดเริ่มของ Duplicate ACK
Exam Tipข้อสอบมักให้ Seq + ขนาดไบต์ แล้วถาม Ack# — แค่บวกเลข: Ack = Seq + Bytes

FLOW CONTROL

Flow Control / Receive Window (rwnd)

กัน "Buffer ล้นที่ฝั่งรับ" — ฝั่งรับบอกว่ามีที่ว่างเท่าไหร่ แล้วผู้ส่งส่งตามนั้น

RECEIVER BUFFER · ฝั่งรับ
Buffer ที่ใช้แล้ว30 KB
Receive Window (rwnd) — ว่าง70 KB

ฝั่งรับประกาศ rwnd ในทุก ACK — ผู้ส่งส่งได้ไม่เกินค่านี้

หลักการ

Flow Control = การควบคุมอัตราส่งของ Sender เพื่อไม่ให้ Receiver Buffer ล้น (ข้อมูลมาเร็วเกินกว่าที่แอปจะประมวลผลทัน)

Sender ต้องรักษา: ส่งไปแล้ว − ได้รับ ACK แล้ว ≤ rwnd

อย่าสับสนFlow Control = ควบคุมตาม ความสามารถฝั่งรับ (rwnd) · Congestion Control = ควบคุมตาม สภาพเครือข่าย (cwnd) — ผู้ส่งต้องช้ากว่าทั้งสอง
จำrwnd ประกาศโดย Receiver ใน TCP Header (Window field) — "ฉันมีที่ว่างเท่านี้ ส่งมาแค่นี้พอ"

CONGESTION CONTROL · AIMD

Congestion Control + AIMD

กัน "เครือข่ายแน่น" — ผู้ส่งค่อย ๆ เร่ง แล้วลดครึ่งเมื่อเจอ Loss — กดปุ่มเพื่อดูกราฟ

CONGESTION WINDOW (cwnd) · AIMD

เริ่ม: cwnd = 1 MSS

AIMD

Additive Increase — เพิ่ม cwnd ทีละ 1 MSS ต่อ RTT (ค่อย ๆ เร่ง ขณะที่ไม่มี Loss)

Multiplicative Decrease — เมื่อเกิด Loss (Timeout / Dup ACK) ลด cwnd ลงครึ่งหนึ่งทันที

เปรียบเหมือนรถ: ค่อย ๆ เพิ่มความเร็วทีละนิด (AI) แต่พอเจอรถติด (Loss) ให้ เบรกครึ่งหนึ่ง (MD) แล้วค่อยเร่งใหม่
Exam TipAI = +1 MSS/RTT · MD = ÷2 เมื่อ Loss — สูตรนี้ติดข้อสอบประจำ

RETRANSMISSION

Timeout / Retransmission / Duplicate ACK

เมื่อข้อมูลหาย TCP รู้ได้ยังไง และส่งซ้ำเมื่อไหร่

Timeout → Retransmission

Sender ตั้ง Timer ไว้สำหรับ Segment ที่ส่งไป ถ้าครบเวลายังไม่ได้รับ ACK → สงสัยว่าหาย → ส่งซ้ำ (Retransmit)

💡 Timeout ยาวเกินไป = ช้า · สั้นเกินไป = ส่งซ้ำเปล่า — TCP จึงปรับเวลาอัตโนมัติตาม RTT

Duplicate ACK ×3 → Fast Retransmit

เมื่อ Receiver ได้ Segment ที่ไม่ต่อเนื่อง (เช่น ตัวกลางหาย) จะ ACK ซ้ำค่าเดิม ทุกครั้ง

เจอ 3 Duplicate ACK ติดกัน = แทบแน่ใจว่าหาย → ส่งซ้ำทันที โดยไม่ต้องรอ Timeout

ACK 1000 ซ้ำ ×3

Receiver ได้ Seg 3 ก่อน Seg 2 → ACK ย้ำค่าเดิม (1000) → Sender สงสัย Seg 2 หาย → Fast Retransmit

จำTimeout = "รอครบเวลา" · Duplicate ACK ×3 = "หลักฐานชัดเจน" → ทั้งคู่ทำให้ส่งซ้ำ แต่ Fast Retransmit ไวกว่า

INTERNET CHECKSUM

Internet Checksum — ตรวจ error แบบง่าย

วิธีตรวจสอบความถูกต้องของข้อมูลที่ Internet ใช้ (เช่น ใน UDP/TCP/IP) — หลักการ 1's complement

ขั้นตอนการคำนวณ (Sender)

  1. แบ่งข้อมูลเป็นชุด 16 บิต เรียงต่อกัน
  2. บวกเลขทุกชุดแบบ 1's complement (ถ้า overflow ให้เอากลับมาบวกที่ bit ล่าง)
  3. แล้ว กลับบิต (complement) ได้ค่า Checksum
  4. แปะ Checksum ลงใน Header แล้วส่ง

การตรวจสอบ (Receiver)

Receiver บวกทุกชุด + Checksum ด้วยกัน — ถ้าข้อมูลถูกต้อง ผลรวม 1's complement ต้องเป็น 11111111 11111111 (FFFF)

ผลไม่ใช่ FFFF → มี Bit Error → ข้อมูลเสีย

ง่ายแต่มีขีดจำกัดจับ error ได้ แต่ไม่รู้ว่ากี่บิต/ตำแหน่งไหน — เทคโนโลยีใหม่ใช้ CRC แข็งแรงกว่า (เช่น ใน Data Link)
จำInternet Checksum = 1's complement sum (16 บิต) — ตรวจ error เบื้องต้น ถูกกว่าและเบากว่าการเข้ารหัส

CHAPTER SUMMARY

สิ่งที่เราเรียนรู้ (บทที่ 4)

รวบรวมประเด็นสำคัญของ Transport Layer ไว้ครบในที่เดียว

Mux / Demux

รวมหลายแอปลงช่องเดียว (Mux) · แยกไปแอปถูกต้อง (Demux) · TCP ใช้ 4-tuple, UDP ใช้ 2 ค่า

TCP vs UDP

TCP เชื่อถือได้ มีลำดับ Flow/Congestion · UDP เร็วเบา Header 8 ไบต์

Reliability

Checksum + Seq# + ACK + Timer/Send ซ้ำ — จาก rdt1.0 (ไม่ตรวจ) → rdt2.0 (ACK/NAK) → rdt3.0 (Timer)

Three-Way Handshake

SYN → SYN-ACK → ACK — เปิด TCP · ปิดด้วย FIN

Seq / Ack

Seq = ไบต์แรก · Ack# = Seq + จำนวนไบต์ที่รับ (Cumulative)

Flow / Congestion

Flow = rwnd (กัน buffer ล้น) · Congestion = cwnd + AIMD (เพิ่ม 1 ลดครึ่ง) · Dup ACK ×3 → Fast Retransmit
